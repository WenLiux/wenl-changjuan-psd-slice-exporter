## Current data flow

```text
CLI arguments
  -> PSDImage.open()
  -> Resource.SLICES
  -> V6 or V7/V8 coordinate extraction
  -> remove any full-canvas slice when multiple records exist
  -> tuple sort
  -> PSDImage.topil()
  -> crop each slice
  -> PNG save
  -> unconditional ZIP creation
```

## 1. PSD/PSB opening

The script opens both formats through:

```python
PSDImage.open(path)
```

No save method is called on the source document. The script only reads the
source and writes new PNG/ZIP artifacts to the requested output location.

Regression tests compare the source byte size, modification timestamp, and
SHA-256 after export. Both real fixtures remained unchanged.

## 2. Slice parsing

### V6

V6 is represented by `psd_tools.psd.image_resources.SlicesV6`.

Each item exposes:

```text
record.bbox = [left, top, right, bottom]
```

The current coordinate mapping is correct for the verified PSB fixture.

### V7 and V8

psd-tools 1.14.2 parses both resource versions 7 and 8 as
`DescriptorBlock`. The script reads:

```text
bounds.Top
bounds.Left
bounds.Btom
bounds.Rght
sliceID
```

The mapping is correct for the verified V8 PSD fixture. There is currently no
real V7 fixture, so V7 compatibility is inferred from the psd-tools reader and
is not yet proven by an end-to-end file.

### Stage 0 regression found and fixed

The previous condition used:

```python
hasattr(slice_data, "items")
```

This was ambiguous:

- `SlicesV6.items` is a list;
- `DescriptorBlock.items` is a method.

As a result, the V8 path attempted to iterate a method and failed with:

```text
TypeError: 'method' object is not iterable
```

The dispatch now uses the explicit resource version:

```python
if slice_resource.version == 6:
```

This restores the previously verified PSD behavior without changing the V6
output.

## 3. Automatic full-canvas slice handling

Current rule:

```text
If there is more than one slice, remove every slice whose bounds equal the
full canvas.
```

This is sufficient for the two known fixtures:

- the V6 fixture has an automatic full-canvas slice with `origin == 0`;
- the V8 fixture has an automatic full-canvas slice whose origin enum is
  `autoGenerated`;
- all 14 content slices are retained.

The rule is not safe enough for production.

Known ambiguous cases:

1. A user-created full-canvas slice plus smaller slices would be deleted.
2. A file containing only one automatic full-canvas slice would export it as
   if it were a user slice.
3. Multiple full-canvas records could produce zero outputs without a clear
   error.
4. Slice origin and slice type metadata are ignored.

Stage 1 must preserve origin metadata and return an ambiguity state instead of
silently deleting a possible user slice.

## 4. Composite image source

The current call is:

```python
psd.topil()
```

In psd-tools 1.14.2, `PSDImage.topil()`:

1. calls `has_preview()`;
2. reads `psd._record.image_data`;
3. converts the stored merged channels into a Pillow image;
4. does not call the layer compositing engine.

`PSDImage.composite()` is the separate method that can fall back to
`composite_pil()` and re-render layers.

Both verified fixtures contain `VERSION_INFO.has_composite == True`,
`has_preview() == True`, and `is_updated() == False`. The current exports
therefore come from the Photoshop-saved merged image data, not third-party
layer re-rendering.

This satisfies the high-fidelity source requirement for the two fixtures.

### Reliability limitation

When `VERSION_INFO` is absent, psd-tools `has_preview()` assumes merged data is
available. Production code needs an explicit `CompositeResult` with:

- source;
- reliability flag;
- dimensions;
- mode;
- warning;
- failure reason.

It must not silently fall back to `psd.composite()`.

## 5. Color and transparency

Both verified fixtures:

- use RGB color mode;
- use 8-bit depth;
- decode as RGBA;
- have alpha extrema from 0 through 255;
- contain no `Resource.ICC_PROFILE`.

The exported PNG files remain RGBA, so transparency is preserved for these
fixtures.

The current call uses the default:

```python
psd.topil(apply_icc=True)
```

If a source contains an ICC profile, psd-tools converts the decoded image to
sRGB. Therefore the current source comment claiming that original pixels are
preserved is too broad: an ICC-bearing file can undergo a color transform.

The script also has no explicit policy for:

- preserving the original ICC profile;
- embedding an sRGB profile;
- reporting a conversion;
- CMYK;
- 16-bit input;
- unsupported Pillow modes.

These behaviors must be made explicit in the later color-management stage.

## 6. PNG export

Current behavior:

- always exports PNG;
- uses `compress_level=6`;
- names files by sequence and output dimensions;
- crops from one decoded full-size composite;
- does not resize;
- does not retain Photoshop slice names.

For both fixtures, all exported PNG files match the verified baseline at the
decoded pixel level.

## 7. ZIP generation

The script always creates a ZIP with:

```python
shutil.make_archive(...)
```

Production differences required by the plan:

- ZIP must be optional;
- ZIP must default to off;
- archive contents must only include files from the current run;
- ZIP failure must not invalidate already successful folder output.

## 8. Current validation

Implemented:

- slice resource exists;
- each slice has positive in-canvas bounds;
- decoded merged image exists;
- Pillow successfully saves each PNG.

Not implemented:

- duplicate slice detection;
- overlap detection;
- gap detection;
- empty or single-color slice warning;
- output reopen verification;
- output count verification;
- dimension verification after save;
- source fingerprint verification;
- stitch-back pixel comparison;
- partial failure reporting;
- JSON/TXT validation reports.

The Stage 0 regression test supplies output reopen, dimension, pixel digest,
ZIP integrity, and source protection checks for the two fixtures.

## 9. Output directory risks

The current script uses:

```python
output.mkdir(parents=True, exist_ok=True)
```

Consequences:

1. Existing same-name PNG files are overwritten.
2. Unrelated stale files remain in the folder.
3. The ZIP can include stale files from previous runs.
4. A failed run can leave partial output.
5. There is no automatic `_02` collision-safe directory.

This behavior is acceptable only for the legacy baseline and must not be
carried into the production export service.

## 10. Sorting and naming

The current tuple sort effectively orders by:

```text
top, left, bottom, right, slice_id
```

The plan requires:

```text
top, left, original_index
```

The difference matters when slices share top and left coordinates. Original
record index and Photoshop slice name are not currently retained.

## 11. Memory and performance

Estimated decoded RGBA sizes:

| Fixture | Canvas | One RGBA canvas |
| --- | ---: | ---: |
| PSD V8 | 1440 x 28164 | about 154.7 MiB |
| PSB V6 | 1440 x 31044 | about 170.5 MiB |

Measured legacy process-tree peaks:

| Fixture | Elapsed | Peak RSS |
| --- | ---: | ---: |
| PSD V8 | 8.323 s | 1566.4 MiB |
| PSB V6 | 9.427 s | 1781.4 MiB |

The measured peak is roughly ten times one decoded RGBA canvas and is the
largest production risk found in Stage 0. Likely contributors include PSD
record storage, merged channel decompression, Pillow channel images, RGBA
merge, alpha un-premultiplication, PNG encoding buffers, and crop copies.

Stage 2/3 must add:

- preflight memory estimation;
- low-memory mode;
- explicit object release;
- measurements that distinguish parser, decode, crop, and encode phases;
- tests on machines with constrained memory.
